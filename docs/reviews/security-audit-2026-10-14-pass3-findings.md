## `ghosted/change-password-limiter-selfreset`

**Verdict:** `rejected` — The only bound on guessing an account's current password is a shared per-IP bucket that the route's own success path deletes

POST /api/auth/change-password is a current-password oracle (wrong password -> 401 INVALID_PASSWORD) whose single limiter is keyed on the client IP and is then deleted by rateLimitSuccess on the success path, in the same scope and identity. Five guesses plus one successful self-service change from the same IP restarts the window, turning the intended 5-per-15-minutes into a bcrypt-bound ~3 guesses/second, with no per-account counter anywhere on this route. Rejected on effect, not on mechanism: the only caller who can reach the oracle already holds the target's session, and the claimed payoff (the password DELETE /api/auth/account demands) is reachable without it.

**Claimed root cause.** rateLimit(getClientIp(req), "change-password") at app/api/auth/change-password/route.ts:22 is the only counter on the route; the success path calls rateLimitSuccess(getClientIp(req), "change-password") at :40, which deletes exactly the key the limiter wrote (lib/utils/rate-limit.ts:79 vs :141), so any successful change-password from the attacker's IP clears the failure budget that protects every account behind that IP.

The arithmetic is overstated by 1.6x - the cycle pays 8 bcrypt ops per 5 guesses once the reset's own hash (account.ts:140) and the re-login the epoch bump forces (account.ts:146, auth.ts:355-357) are counted, giving ~2.9 guesses/s, not 4.6 - but the throughput escalation is real and the reset is not a documented or test-pinned trade-off (unlike the register analogue pass 2 rejected), so no 'intended behaviour' defence applies. What fails is the impact. The oracle is reachable only by a caller who already holds the target account's session (route.ts:20, account.ts:133-138), and the specific payoff the candidate claims - the credential DELETE /api/auth/account demands (account/route.ts:70-78) - is obtainable by that same attacker without ever knowing the current password: PATCH /api/auth/profile moves the email with no password (profile/route.ts:11-28; validation.ts:175-190; account.ts:46-65), forgot-password gates only on the account having a passwordHash and mails the token to the attacker's address (forgot-password/route.ts:60-67, :91), reset-password installs an attacker-chosen hash, and the deletion route then accepts it, with a CSRF token anyone can mint (lib/utils/csrf.ts:60-101; @auth/core pages/index.js:37-38). The repo's own precedent rates the deletion password gate as defense in depth, LOW (docs/reviews/pentest-local-2026-10-14.md:92-102), and the other destructive action a session affords (import?mode=replace, lib/services/import.ts:168-170) needs no password at all. So the candidate is not a duplicate of pass 2's register finding - the accelerated oracle here is proof of a secret, not a published enum, and two of pass 2's three rejection grounds genuinely do not transfer - but it dies on the ground that does transfer: an attacker who already owns the session gains no capability it did not already have, and the only thing left is the plaintext secret's reuse value on other services, which is off-app. Honest ceiling: LOW / defense in depth - a soft anti-abuse counter that its own success path clears, worth fixing in one line, not a finding. Minimal fix: delete app/api/auth/change-password/route.ts:40 (the rateLimitSuccess call) and the now-unused import at :13, so a success keeps the slot it already spent at :22; better, for the per-user parity docs/API.md:19 promises, add rateLimitAccount(userId, "change-password") beside :22 and clear only that on success (matching key `acct:change-password:<userId>` - mind login-throttle.ts:37-38's near-miss warning: rateLimitAccount writes the `acct:` prefix, so the reset must name the same scope), touching route.ts:10-14, :22-23 and :40. The identical misfire recurs at app/api/auth/set-password/route.ts:41 (and, already rejected, register/route.ts:130); the general rule is that a shared per-IP bucket must not be cleared by a per-account success. Correction factored in: verifier-17 measured that @auth/core sets the session token with no Domain attribute (lib/utils/cookie.js:48-55) and the app sets no cookies override (lib/auth.ts:91-95), so the cookie is host-only and the candidate's same-site-sibling-foothold reachability leg is dead - the hunter's own SameSite control is stronger than it claimed. The verdict does not rest on that leg: on the one surviving leg, a genuinely stolen session used from the attacker's own client, both the oracle and the profile+forgot bypass are available (PATCH is only stopped cross-origin, never for a copied cookie), so the collision of the two paths is exact and the rejection is unchanged; on the edge-fronted deployment the attacker's own changes must also originate from the same real address the guesses come from (SECURITY.md:67-74). Separately, and independent of how reachable the reset is: the missing per-user counter is a defect in its own right. docs/API.md:19 promises state-changing endpoints are limited per IP and per user and this one is not; lib/utils/rate-limit.ts:166-168 states the per-IP key is 'never the only thing standing between an attacker and an account' because the account and global counters are header-independent, and this route has neither; and the repo's own pentest listed /api/auth/change-password among the routes a single forged X-Forwarded-For resets (docs/reviews/pentest-local-2026-10-14.md:78-84), a finding whose recorded fix (:265) covered only the sign-in counters - so on a directly reachable self-hosted origin the route's sole bound is client-supplied, and the reset is not even needed. That defect is real and independent of the reset, but its severity is capped by the same impact analysis, so it is the same LOW hardening item and the same one-line fix - and it is the reason the fix should be the per-user counter rather than only deleting :40.

## `ghosted/change-password-verify-timing-oracle`

**Verdict:** `rejected` — The success path of change-password costs one extra bcrypt, so an unreadable cross-origin response still answers 'was that the password'

The two exits of POST /api/auth/change-password do different work - a wrong current password ends after one bcrypt.compare (lib/services/account.ts:103-106), a right one continues into a second bcrypt.hash plus an UPDATE (lib/services/account.ts:140-148) - and the route sets no Access-Control-Allow-Origin, so the candidate argues the ~221 ms difference turns an opaque POST into a per-guess oracle on the account's current password. The work asymmetry is confirmed exactly as claimed (and re-measured in isolation: compare 217 ms, hash 221 ms at cost 12). The candidate is rejected because the caller it needs does not exist: the session cookie is host-only (no Domain attribute, no cookies override, no @auth/core domain inference), so a same-site sibling-subdomain foothold never attaches it - measured in real Chrome 154 - and without the cookie requireSession answers 401 UNAUTHORIZED before any bcrypt, identically for a right and a wrong password. The only shape that does attach the cookie is script on the app's own origin, where the status and body are readable directly and the timing channel is unnecessary. What survives is a hygiene note: hash a dummy value (or floor the response) on the failure branch, and correct the repository's own belief that SameSite=Lax carries the session cookie to a sibling subdomain.

**Claimed root cause.** The two exits of POST /api/auth/change-password do different work: a wrong current password ends after one bcrypt.compare (lib/services/account.ts:103-106) while a right one continues into a second bcrypt.hash plus an UPDATE (lib/services/account.ts:140-148). A same-site initiator gets no Access-Control-Allow-Origin, so the status is unreadable, but the response time carries the 219 ms difference the extra hash costs - which turns an opaque POST into a per-guess oracle on the account's current password, the same secret the first candidate is about.

The only other shape that attaches the cookie is a different port on the app's own host (cookies ignore port), which the edge-only deployment does not offer (DEPLOYMENT.md:97-106, SECURITY.md:67-74) and which over http would fail on the cookie's Secure flag anyway. The channel would be measurable; it is unreachable. ## `ghosted/email-change-does-not-revoke-sessions`

**Verdict:** `needs_validation` — Changing the account email moves no session epoch, proves no password and notifies nobody, so a session-only attacker can relocate the account's sign-in identifier and recovery address and then mint a password of their own through forgot-password — a durable credential that outlives the epoch revocation the victim's own reset performs

The trace holds, and the impact is worse than the hunter claimed rather than weaker. `updateProfile` writes `email`, `emailVerified=false` and `emailVerifiedAt=null` and never `sessionEpoch` (lib/services/account.ts:59-64, UPDATE at 70-74), so the compare at lib/auth.ts:355-356 sees the value it saw before and every already-issued token keeps resolving; @auth/core runs that callback on every session read with no `user` (node_modules/.pnpm/@auth+core@0.41.3/node_modules/@auth/core/lib/actions/session.js:28-33), so there is no delayed catch either. The route asks for a session and nothing else (app/api/auth/profile/route.ts:11 -> lib/utils/api.ts:95-127): no current password, no re-authentication. Three corrections to the hunter's chain, all in the direction of the finding being stronger: (1) The victim's password change is NOT a required link. Once the address points at the attacker's mailbox the attacker completes forgot-password themselves and sets a password they chose; waiting for the victim to act only obscures that the attack is a single-actor, three-request chain. It also does not need the router's own verification of the new address — forgot-password gates on `passwordHash` alone (app/api/auth/forgot-password/route.ts:60-67) and never on `emailVerified`, so the reset link for an address that was never verified goes out anyway. (2) The silence is stronger than 'no notice to the old address'. The settings page renders `user.email` from the *token* (app/(dashboard)/settings/page.tsx:37 via lib/auth/current-user.ts:29-33), and the jwt callback only rewrites `token.email` at sign-in or on a client-driven `trigger === "update"` (lib/auth.ts:232-239); an attacker's server-side PATCH never triggers either, so the victim's own Settings page and header keep displaying the OLD address while the row, the login lookup (lib/auth.ts:129-133) and every recovery path point at the attacker's. The victim is not merely un-notified; the app shows them the pre-attack truth. (3) The omission contradicts the control's own definition, not just a documentation list: lib/services/account.ts:124-126 defines the bump as being called from every path that changes how the account can be entered, and the email is the entry key (`authorize()` is a lookup on `users.email`, lib/auth.ts:129-133). The four writers are exactly as the hunter says and I found no fifth (lib/services/account.ts:146, 188; lib/services/oauth-accounts.ts:229; app/api/auth/reset-password/route.ts:69) — the hunter's matrix claim survives a full enumeration of every write to the `users` row in app/, lib/ and scripts/, and no event is missing from the revoking column. Two rows are missing from the non-revoking column (see disproof_attempted 1). On the fix: bumping `sessionEpoch` on the email change does not close this chain, and testing it honestly is the important part of this verdict. The bump evicts the stolen cookie at the change, but the attacker already owns the mailboxes on both ends: they immediately run forgot-password against the address they just installed, receive the link, and set their own password (app/api/auth/reset-password/route.ts:61-71), which is itself an epoch bump. All the bump changes is which attacker credential survives — a chosen password instead of a copied cookie — and it costs the victim their own session (SECURITY.md:46-48: 'the session that makes the change is revoked with the others — the UI signs out and says so'), which is a sign-out with no reason attached rather than a control. The honest remediation is re-authentication: prove the current password before the address may move, exactly as changePassword and deleteAccount already do (the shared helper's own docstring, lib/services/account.ts:78-84: 'Shared by the two places a password is *proved* before something destructive happens'), plus a notice to the OLD address, which is the only control that still works when the attacker holds the session and the password both. The case for re-authentication is strong — it is the same standard two sibling routes already meet, it is one `verifyPassword` call on a route that already imports from the same service, and it is the only one of the three candidate controls that denies the attacker the move instead of reacting to it. The case for the old-address notice is strong and independent. The case for the epoch bump is moderate and deliberately secondary: consistency, and it stops the attacker keeping the copied cookie as well. Rejecting the candidate would require one of the brief's three rejection grounds and none applies — the effect does cross a boundary the app draws for itself (a credential change takes proof; only a session is asked here, and a password-holding account's `changePassword` and `setPassword` refusals at account.ts:138, 174-180 make the email change the unique session-only route to a durable credential), nothing in a framework, config or the database neutralises it (SameSite=Lax kills only the cross-origin variant, which is not the one being used, and the attacker holds the cookie), and it is neither documented as intended nor test-pinned as intended (SECURITY.md:108-115 treats an email move as an attack step and fixed only the token-rebinding half of it). `confirmed` is unavailable for the reason the brief gives — this pass cannot run target code — so `needs_validation`, with the honest statement that the missing evidence is execution and a deployed mail transport, not a repository fact. Honest ceiling: MEDIUM — post-compromise persistence that defeats the documented revocation guarantee, converts a time-bounded session into a permanent credential and locks the victim out of their own sign-in identity, but requires a live session first (the attacker could already read and write all of the account's data), so it is not an unauthenticated takeover and must not be presented as one.

## `ghosted/limiter-map-evicts-live-windows`

**Verdict:** `rejected` — The shared bucket map's overflow prune drops live windows by age, and identities minted in an unrelated scope can aim it at the per-account sign-in cap

The prune in lib/utils/rate-limit.ts (one Map for every scope, oldest-tenth drop above 10,000 live windows) genuinely deletes live, non-expired windows, and a flood of register/forgot-password identities can out-age a target's `acct:login:<address>` bucket (not name it). Real mechanism, rate/hygiene effect, no boundary crossing.

An unthrottled flood of the cheapest possible route is a generic, unbounded-ingress property shared with every other route and with Next.js itself; it is not a boundary crossing and the brief says so explicitly. Confidentiality: the token is 256 bits and single-use (account.ts:237, :233-235), so no request volume forges or induces a verification and no confusion of the deputy is needed by anyone who already has the token. The state-changing-GET half fails twice on its own terms: the emailed link targets the page, not the API (emails.ts:181) and the page's only token handling is a browser useEffect (verify-email-form.tsx:27-36) over a component that renders nothing server-side, so a prefetcher, image tag or non-rendering mail scanner consumes nothing; and the Referer channel is closed by next.config.mjs:23's 'strict-origin-when-cross-origin', which strips path and query from every cross-origin request originating at that URL. The residual - a JS-rendering security scanner burning a one-time link, forcing the user to request another - is usability, is unproven in production (no repository evidence), and the token-in-a-URL shape it rests on is an explicitly accepted MVP trade-off (CHANGELOG.md:1832-1834). VERDICT AND DISPOSITION: rejected. Honest disposition of the surviving material: a documentation defect, not a finding. Two lines are false as written - docs/API.md:185's 'rate limited per IP' and docs/API.md:19's 'State-changing endpoints are rate limited per IP and per user' (also false for app/api/auth/dismiss-password-notice/route.ts, which has no limiter either, so the hunter's 'only ... route' framing is wrong). Hygiene, not a finding, is the rest: no limiter, no CAPTCHA, no visible edge rule. Ceiling: LOW, documentation defect - the fix is to delete the clause or add the limiter (one import plus one call, matching reset-password's getClientIp/rateLimit/rateLimitSuccess trio), not a security remediation. No boundary is crossed, nothing is inflated, nothing is deflated: this candidate is a correct observation about docs and a wrong observation about risk. DUPLICATION (question 5): the doc-vs-code discrepancy is already recorded in pass 2, not as a filed finding but inside the evidence of ghosted/verify-token-address-rebind-race (run-2 findings.json; docs/reviews/security-audit-2026-10-14-pass2-findings.md:382: 'Documents "rate limited per IP" for GET /auth/verify-email; the route implements none. The accelerator is real (the documentation is wrong about it), but it is a rate-limiting gap, not the mechanism.'). Since that is the entire surviving content of this candidate, the honest statement is that it re-reports an already-recorded observation as if it were a new finding. RUN-2 REJECTED ANALOGUE: ghosted/register-ip-budget-cleared-on-success was rejected for buying rate rather than capability; this candidate is weaker still, because it does not even buy rate - one request costs one cheap query, and no expensive work sits behind it.

## `ghosted/write-throttle-window-2500-days`

**Verdict:** `rejected` — Same unit mismatch at lib/utils/api.ts:116: the per-user write throttle is 300 writes per ~2,500 days, not per hour - mechanism confirmed, direction inverted: this is a LOW availability lockout of legitimate users, not the removal of a control for an attacker

Re-read in the worktree: requireSessionForWrite builds its own override in milliseconds (lib/utils/api.ts:113-116, windowMinutes = RATE_LIMIT_WRITES_WINDOW_MINUTES ?? 60, then windowMs: windowMinutes * 60_000) and the callee multiplies that expression by 60_000 a second time (lib/utils/rate-limit.ts:62-67), so the write bucket's resetAt is now + 60 * 60_000 * 60_000 = 216,000,000,000 ms = 2,500 days. The candidate's arithmetic and every one of its source citations re-check; its root cause is right, and it is the same line as the sign-in cap's bug reached through the other call site. What does not survive is the impact claim. The candidate asserts that a stolen or shared session 'can write without any rate bound for the life of the process' and that a documented hardening control has been removed. Both are false in direction. rateLimit counts every call and refuses only when count > max (lib/utils/rate-limit.ts:88-94); the bucket is created once with resetAt = firstWrite + windowMs (:82-85) and resetAt is never extended or rewritten; and no caller clears a write scope (verified at all six rateLimitSuccess call sites). Under the 2,500-day window the permitted set is therefore {the first 300 writes per scope until the process exits}, a strict subset of {the first 300 writes per hour, indefinitely} that the intended window permits - every request the bug allows the intended code also allows, and the converse fails. A longer window with the same max is 60,000x tighter in aggregate; it is the lost hourly pacing, not a lost cap. No trust boundary is crossed either way: the bucket is keyed per user id (lib/utils/rate-limit.ts:133, key acct:write:<scope>:<userId>), so no actor can spend, fill or clear another user's write budget, and the only party who reaches the guard has already authenticated. What is real is the availability defect the candidate never looks at: because nothing clears the bucket on success, the counter is cumulative over the process lifetime, and the 'applications' scope alone absorbs six routes (create, edit including a board drag, delete, favorite, reopen, timeline reset) under one 300 budget. The repository's own e2e stress test creates 220 applications in one session (tests/e2e/stress.spec.ts:13-31, TOTAL = 220), 73% of the budget before a single edit, favorite, reopen or drag; the guard even runs before body parsing, so rejected writes also spend budget. When it trips the user gets 429 RATE_LIMITED with no Retry-After on every write in that scope, the board rolls back the optimistic move and shows 'Too many requests, please try again later', and nothing recovers it short of a process restart or redeploy - the write bucket, at 2,500 days, is the most eviction-resistant entry in the shared map and the last row of the oldest-tenth sort. Honest ceiling: LOW availability defect for legitimate users, worth a one-line fix in the callee, not a security finding.

**Claimed root cause.** requireSessionForWrite builds the override itself (windowMs: windowMinutes * 60_000, already milliseconds) and limits() multiplies it by 60,000 again, so the documented 300-writes-per-hour ceiling (lib/utils/api.ts:87-94) becomes 300 writes per 216,000,000,000 ms. It is the same line as the sign-in cap's bug (lib/utils/rate-limit.ts:66) reached through the other call site.

**Rejection reason.** Rejected on effect, not on mechanism - and the effect is inverted. The trace re-checks line for line: requireSessionForWrite converts minutes to milliseconds itself (lib/utils/api.ts:113-116; .env.example:127 sets 60) and limits() multiplies the entire override expression by 60_000 again (lib/utils/rate-limit.ts:62-67), so the write bucket's resetAt is now + 60 * 60_000 * 60_000 = 216,000,000,000 ms = 2,500 days. The parent's arithmetic and the sign-in side of the same line are taken as given and were not re-derived. Every citation in the candidate is accurate; the one imprecision is api.ts:87, which is the docstring block that opens at :87 while the quoted 'Default 300 writes/hour' is at :89 - a pointer to the block, not a wrong claim. Its blocker is also correct: nothing in the repository pins the write throttle. (1) WHICH DIRECTION THE BUG BITES. Only the availability direction is real, and the hunter's is refuted. rateLimit increments count on every call and refuses only when count > max (lib/utils/rate-limit.ts:88-94); the bucket is created once with resetAt = firstWrite + windowMs (:82-85); resetAt is never extended or rewritten; and nothing clears it - I checked all six rateLimitSuccess call sites (login/route.ts:72, register/route.ts:130-131, reset-password/route.ts:90, change-password/route.ts:40, set-password/route.ts:41, lib/auth/login-throttle.ts:100) and none passes a write scope, and the only other mutations of the map are the expired sweep at :36 and the oldest-tenth drop at :48. So the buggy permitted set is {the first 300 writes per scope until the process exits}, a strict subset of {the first 300 writes per hour, indefinitely}. Every write the bug permits, the intended control also permits; writes 301-600 in the second hour are refused only by the bug. A longer window with the same max cannot remove a cap - it makes it 60,000x tighter in aggregate and merely drops the hourly pacing. 'A stolen or shared session can write without any rate bound for the life of the process' is therefore false, and so is 'it removes a documented hardening control for an already-authenticated attacker': a stolen session is strictly worse off than the docstring promised. Nothing crosses a trust boundary in either direction, because the bucket is keyed per user id (lib/utils/rate-limit.ts:133, key acct:write:<scope>:<userId>), so no actor can spend, fill or clear another user's budget, and the only party who reaches the guard has already authenticated. (2) IS 300 REACHABLE IN NORMAL USE. Yes, and the bug is a cumulative cap rather than an hourly one, so the pattern is 'enough activity ever' rather than 'a busy hour'. The guard takes six scope strings ('applications', 'milestones', 'profile', 'account', 'import', 'export'), each with its own 300; the 'applications' scope alone absorbs six routes - create an application (app/api/applications/route.ts:35), edit it including every board drag (app/api/applications/[id]/route.ts:41), delete (:72), toggle favorite (.../favorite:17), reopen (.../reopen:17) and reset the timeline (.../milestones/reset:21) - and the 'milestones' scope absorbs create, update and delete (app/api/applications/[id]/milestones:17, app/api/milestones/[id]:20, :50). The guard runs before the body is parsed (applications/route.ts:35 precedes :37), so rejected and malformed writes spend the budget too. The numbers that make this concrete are the repository's own: the docstring justifies the allowance as 'generous enough for bulk entry of applications (a real job-seeker can add dozens in a sitting)' (lib/utils/api.ts:89-91), and tests/e2e/stress.spec.ts:13-31 creates 220 applications through POST /api/applications in one registered session - 73% of the budget in one test run, before any edit, favorite, reopen or drag. A verified user (UNVERIFIED_APP_LIMIT=3 caps only unverified accounts, lib/services/applications.ts:591-593) who imports or bulk-enters 300+ applications, or who accumulates 300 create/edit/delete/favorite/reopen/reset calls on a real board - 300 drags between columns is a few months of ordinary heavy use - is locked out of the 'applications' scope. (3) WHAT THE USER EXPERIENCES, AND WHETHER ANYTHING RECOVERS IT. Every write in that scope returns HTTP 429 with {error: 'Too many requests, please try again later', code: 'RATE_LIMITED'} and no Retry-After header - requireSessionForWrite throws a bare ApiError (lib/utils/api.ts:118-125) that handleRouteError maps at :42-45, unlike rateLimited() at :130-138 and the DB_UNAVAILABLE branch at :60-66, so the client is told nothing about when it lifts (the honest answer is 216,000,000 seconds). In the board the optimistic move is rolled back and the message is printed verbatim (components/KanbanBoard.tsx:141-149): the card snaps back and says 'try again later' when the window is 2,500 days. Reads, sign-in, export and the other scopes keep working, so it is a write lockout in one scope, not a lockout from the app. Nothing recovers it short of a process restart or redeploy: the map is module-scope (lib/utils/rate-limit.ts:19), never cleared wholesale, no write path calls rateLimitSuccess, and the 2,500-day bucket is the most eviction-resistant row in the oldest-tenth sort at :43-49. Per-replica counters (SECURITY.md:75-79) make the experience worse, not better - with more than one replica the user's writes land on a partially poisoned budget and fail intermittently. (4) DISPOSITION AND CEILING. Availability defect for legitimate users only. Both candidate dispositions are wrong as stated: 'hardening removal for an attacker' is refuted in direction, and 'both' is refuted because the mechanism cannot help any attacker - not an unauthenticated one (the guard is inside requireSessionForWrite, behind a session) and not an authenticated one (whose own budget is the thing that shrinks). The honest ceiling is LOW: a real functional/availability bug that locks a user out of their own writes in one scope for the life of the process, cannot touch another user's data, authority or budget, and clears on restart. That is why this is rejected rather than needs_validation: both decisive facts are fully in the repository - the direction, from :82-94 plus the absence of any clearing call, and the reachability, from the route inventory plus the repo's own 220-application stress test - and neither a clock-advanced run nor a deployment fact would change either one. A runtime would only add the wall-clock life of the production process, which moves how often the lockout is hit, not whether it exists or which way it points. (5) MINIMAL CORRECT FIX AND WHETHER THE PIN NEEDS A CLOCK. Fix the unit conflict in the callee, one line: `overrides?.windowMs ?? Number(process.env.RATE_LIMIT_WINDOW_MINUTES ?? 15) * 60_000` at lib/utils/rate-limit.ts:62-67, so only the minutes-valued env default is converted and a caller-supplied windowMs is taken as milliseconds. That repairs both call sites and both candidates at once (lib/utils/api.ts:116 and lib/auth/login-throttle.ts:64), keeps the env names and the `windowMs` field name meaning what they say, and cannot break a third caller: a tree-wide grep for windowMs outside the limiter returns only those two sites, and both pass milliseconds. The regression pin needs a clock, and cannot be written without one: the contract is a duration (the 300th write inside the window is permitted, the 301st is refused, and the window lifts when it elapses), and neither the bucket's resetAt nor limits() is exported, so the only non-clock assertion available would be a source-shaped one - exactly the anti-pattern the test-audit gate exists to stop. Under vi.useFakeTimers a cheap limiter-level test pins the override-as-ms contract (301 calls to rateLimitAccount(id, 'write:x', {max: 300, windowMs: 3_600_000}) with the 301st refused, then advance 3_600_001 ms and assert success), and a route-level test over POST /api/applications with a mocked session pins the guard end to end. There is no coverage of the write throttle at all today, so this is a new file and the test-audit authoring gate applies.
