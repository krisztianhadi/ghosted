## `ghosted/authenticated-pages-cacheable`

**Verdict:** `rejected` — Authenticated HTML pages are served with no Cache-Control at all; the no-store rule covers only /api/* and the page response carries neither a directive nor a Set-Cookie

Claims that in Next 15.5.27 the App Router emits no Cache-Control on page responses and that middleware scopes no-store to /api/*, so an intermediary that caches extensionless HTML would key the dashboard on a cache key without the session (Vary has no Cookie) and could serve one signed-in user's page to another. The framework half of that claim is false: a dynamic App Router page response in the installed 15.5.27 carries `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`, set by the framework, not by the app.

**Claimed root cause.** middleware sets Cache-Control: no-store only when pathname.startsWith('/api/'), and next.config.mjs headers() adds no cache directive. In Next 15.5.27 the App Router emits no Cache-Control for page responses: the app-page build template sets only Vary, the app-page runtime's only Cache-Control literal is the server-action one, and the module that produces s-maxage/private-no-cache headers is imported exclusively by Pages-Router paths. The RSC session read that guards these pages also discards any Set-Cookie, so nothing in the response tells an intermediary to keep its hands off.

## `ghosted/csrf-missing-on-write-routes`

**Verdict:** `rejected` — Every write route except account deletion and replace-import is guarded by SameSite=Lax alone: requireSessionForWrite asks for no CSRF token, and no Origin/Referer check exists

The mechanism is real and I reproduced it by reading: requireSessionForWrite (lib/utils/api.ts:95) authenticates a session, refuses a forced password change and applies a per-account throttle, with no CSRF token and no origin argument; verifyCsrfToken is called in exactly two places (app/api/auth/account/route.ts:38 and app/api/auth/import/route.ts:107, the latter only for ?mode=replace); and nothing in middleware.ts, next.config.mjs or any handler reads Origin or Referer. Fifteen session-authenticated mutating handlers sit behind that posture. The claimed exploit does not survive: the email-change step is PATCH /api/auth/profile, PATCH is not a CORS-safelisted method, so a same-site sibling-subdomain origin must pass a preflight and the app returns no Access-Control-Allow-Origin — the repo measured exactly this for the analogous DELETE at docs/reviews/pentest-local-2026-10-14.md:100-101. The XSS leg is not a CSRF gain either, because GET /api/auth/csrf hands the token to any same-origin script (lib/pages/index.js:23-34). What remains is a real defense-in-depth gap: a foothold on a subdomain the owner controls can still issue CORS-simple POSTs, of which POST /api/auth/set-password (first password on a provider-only account) is a credential takeover and POST /api/auth/import?mode=merge, POST /api/applications and POST .../milestones/reset are data tampering. That is the same class of gap the repo already recorded and rated LOW / defense in depth for the deletion route (pentest-local-2026-10-14.md:92), and SECURITY.md:92-97 plus docs/API.md:186,192 document the token as the control for the hard-delete paths only — so the omission elsewhere is a deliberate, documented scope choice, not a bug against the app's own policy.

**Claimed root cause.** requireSessionForWrite (lib/utils/api.ts:95) enforces only a session, a mustChangePassword gate and a per-account rate limit, so the write routes authenticate the caller and then mutate without any proof the request came from the app's own page; verifyCsrfToken is called only by account deletion and ?mode=replace import, and no Origin/Referer check exists.

If the project wants the deletion-route standard applied everywhere, the fix is one line in requireSessionForWrite — verify the Auth.js token there, or compare Origin against the configured site origin for every state-changing route — but on the deployed shape as documented, nothing crosses a trust boundary that the cookie's SameSite=Lax and the browser's CORS preflight leave open.

## `ghosted/forgot-password-timing-enumeration`

**Verdict:** `needs_validation` — forgot-password answers identically in status and body on every path, but the response path is not equalised: the exists-with-a-password branch performs three extra statements and awaits a full mail-transport conversation before the 200

POST /api/auth/forgot-password returns `200 {ok:true}` from every branch, and the code comment at route.ts:58, docs/API.md:183 and the test name at tests/integration/auth.test.ts:245 all claim 'no account enumeration'. Only the status and body are equalised. The work on the response path is not: a miss performs one prepared SELECT (52-56) and answers; a hit whose account has a password additionally performs a second SELECT (61-65), a DELETE (71-81), an INSERT (85-89) and then `await sendPasswordResetEmail(...)` (91), which on a delivering transport is an outbound round trip (resend.ts:14, an HTTPS POST to api.resend.com, or the whole SMTP conversation at smtp.ts:311+). A third class — the account exists but is OAuth-only — performs the second SELECT and then answers without sending, so it sits between the other two. The mechanism is fully established from source: no `after()`/`waitUntil`, no queue, no fixed delay, no jitter and no documented acceptance exists anywhere in the repository, and the installed Next 15.5.27 ships the deferral API that would fix it but does not use it. What is not established is the realised magnitude: that depends on which transport each deployment resolves (a deployment fact, not a repository fact), on the Resend round-trip latency and the edge jitter in front of it, and on the production RATE_LIMIT_MAX and replica count that SECURITY.md:75-78 says is greater than one. The access is bounded to 480 probes/day per source IP per replica by rateLimit(ip,"forgot-password") (5/15 min, process-local, rate-limit.ts:19,58-67), but the per-address counter (47) cannot bind a sweep of distinct addresses, and a targeted single-address check needs one request, so the budget is not a control on the real use case. Honest ceiling: LOW — CWE-203/CWE-208, membership disclosure only, no session, no token, no data, no auth bypass; reportable because it falsifies a property the code and the docs both promise, but it must not be inflated past 'the attacker learns whether an address has an account'. The hunter's secondary claim (a password account is separable from a provider-only one) is one indexed SELECT, roughly single-digit milliseconds, and is more likely than not below edge jitter per sample; it should be treated as unproven until measured, not as part of the confirmed delta.

**Claimed root cause.** The route is written to answer identically, and the status and body are identical, but the work is not: for an address that exists with a passwordHash it runs three extra statements (a passwordHash select, the stale-token delete, the token insert) and then awaits a whole mail send (app/api/auth/forgot-password/route.ts:91); for an address that does not exist it returns after one SELECT (route.ts:52-56). The clock is therefore an existence oracle on the reset surface.

The log shape is the causal control — if the delta survives it, the send is not the cause. (3) The privacy-preserving variant of the same run: instead of timing the HTTP response, monkey-patch nothing and simply assert the branch statement counts with a query logger, confirming DELETE+INSERT+send fire only for class C; that establishes the mechanism but not the observability, and must be reported as such.

## `ghosted/login-csrf-custom-login-route`

**Verdict:** `needs_validation` — POST /api/auth/login mints a session for a cross-site caller: no CSRF token, no Origin check, no Content-Type assertion, and no session cookie for SameSite=Lax to withhold

The app's own credentials endpoint re-implements Auth.js's sign-in while dropping the double-submit token the framework endpoint enforces for credentials providers (@auth/core/lib/index.js:53-55, skipped by design at next-auth/lib/actions.js:44). Because the route must work for a caller with no session, SameSite=Lax withholds nothing, and nothing compares Origin, Referer or Sec-Fetch-Site. A hostile page can therefore plant a session for an account the attacker owns into the victim's browser; the victim's subsequent applications, milestones and notes are written into the attacker's account and the victim's own session is gone. Measured in this machine's real Chrome 154 on throwaway origins (no target code): a cross-site top-level form POST with enctype=text/plain delivers a parseable JSON body with no preflight, and the SameSite=Lax cookie on that response IS stored — the shape that browser refuses is the cross-site no-cors fetch, not the form POST. Login CSRF, not account takeover: nothing about the victim's credential changes.

## `ghosted/smtp-multiline-reply-code-confusion`

**Verdict:** `rejected` — A multiline reply whose continuation lines carry a different code resolves to the first code, so a rejection can be read as success

Verified mechanism: a multi-line SMTP reply in which a continuation line carries a code different from the first line resolves to the first line's code and silently drops the other line's text. Concretely, `250-ok` + `550 nope` produces {code: 250, lines: ['ok']} from SmtpSession.onData_, the string 'nope' is discarded before any consumer sees it, and expect(reply, [250], 'message body') at lib/email/smtp.ts:392 passes. A rejection by the peer is therefore recorded as an accepted send. The mechanism is real; the security effect is not.

**Claimed root cause.** The data handler keeps a reply open until a line uses a space separator, but only records a line when its code equals the in-progress code (smtp.ts:128); a line carrying a different code is silently dropped, and the terminating line still resolves the reply using the first code and the truncated line list. expect() then compares only that first code, so a peer answering '250-ok' followed by '550 rejected' yields code 250 with lines ['ok'] and the step passes.

**Trace**

- `entrypoint` — `lib/email/smtp.ts:119`
- `propagation` — `lib/email/smtp.ts:128`
- `propagation` — `lib/email/smtp.ts:132`
- `propagation` — `lib/email/smtp.ts:213`
- `sink` — `lib/emails.ts:41`

**Evidence**

- `lib/email/smtp.ts:128` — The drop condition: a foreign-code line is neither recorded nor allowed to change replyCode.
- `lib/email/smtp.ts:133` — The reply object is built from the retained replyCode and the filtered replyLines, which is where the terminating line's own code and text are lost.
- `lib/email/smtp.ts:213` — expect() compares reply.code only, so the truncated reply decides the step.
- `lib/emails.ts:41` — sendEmail turns a non-throwing transport call into 'email sent' plus true (literal at 43, return at 45).
- `tests/unit/smtp.test.ts:527` — The only refusal test, and it is a single-line 550 (fake's reply at 234), so the mixed-code path is untested.
- `tests/unit/smtp.test.ts:436` — The repo's only multiline-reply pin; it exercises chunk splitting with same-code 250 continuation lines (fake builds them at 205-210), so it neither covers nor endorses a code change inside one reply.
- `app/api/auth/resend-verification/route.ts:36` — The only security-adjacent consumer of the boolean; false becomes 502, true becomes {ok:true}, and issueEmailVerification already ran at 29 so no account state is gated on it.
- `lib/email/transport.ts:81` — The SMTP peer is fixed by the operator's SMTP_URL (parsed here into the transport config) and is unreachable from any request path, so the only party able to emit the malformed reply is the operator's own configured relay.

**Rejection reason.** Rejected on effect, not on mechanism. (1) The trace re-checks exactly: SmtpSession.onData_ (lib/email/smtp.ts:119-142) discards any line whose code differs from this.replyCode (line 128) yet still treats that line's space separator as the reply terminator (132-138), so `250-ok` + `550 nope` resolves to {code: 250, lines: ['ok']}, expect(...[250]...'message body') at 392 passes, and 'nope' never reaches even the error string at 214. The hunter's mechanics and its disproof #1 are both correct. (2) A conforming peer cannot produce the input: RFC 5321 §4.2.1 says 'In a multiline reply, the reply code on each of the lines MUST be the same. It is reasonable for the client to rely on this, so it can make processing decisions based on the code in any line' — so using the first line's code is the reliance the standard sanctions, and mixed codes require an RFC-violating server. No test, config or doc in the worktree pins or excuses mixed codes either; tests/unit/smtp.test.ts:436 pins only same-code continuation. (3) No trust boundary is crossed however the peer behaves. The only party that can emit the malformed reply is the configured relay (SMTP_URL is operator-only, lib/email/transport.ts), and that peer already decides acceptance unilaterally: a peer willing to misreport writes a conforming `250 ok` at 392 and gets byte-identical results, so the parse quirk grants an adversary nothing it did not already have. (4) Nothing security-relevant consumes the laundered success: resend-verification is the only reader of the boolean (30-41, false -> 502), register (114), profile (27) and forgot-password (91) discard it, and issueEmailVerification always runs before the send, so no token, verification flag, session or authorization state depends on it. The observable delta is one false 'email sent' log line and an HTTP status. Honest ceiling: a robustness/honesty defect of informational severity, worth at most a defensive fix (treat a code change inside one reply as a protocol error, or resolve on the terminating line's code) — it can never be elevated to a boundary crossing, because the peer is the acceptance authority and can lie conformingly at will. That is why this is `rejected` rather than `needs_validation`: both decisive facts — the standard's requirement and every consumer of the boolean — are fully in hand, and neither a real relay that emits mixed codes nor one that does not changes the security outcome.

## `ghosted/smtp-unbounded-reply-read`

**Verdict:** `rejected` — The SMTP reply reader is bounded only by socket inactivity, so a peer that keeps sending never lets a reply complete and grows app memory without limit

SmtpSession arms exactly one watchdog, net.Socket.setTimeout(20s), which is an inactivity timer; readReply() has no deadline, no AbortSignal and no cap on the input buffer or on the accumulated reply lines. A peer that emits continuation lines or raw bytes faster than the 20s idle boundary therefore keeps every protocol step pending forever, and each such session buffers without limit. Claimed impact: denial of service against the app's own mail path plus unbounded memory growth, reachable only by the configured SMTP peer.

**Claimed root cause.** SmtpSession arms exactly one watchdog: net.Socket.setTimeout(20s). Node defines that as an inactivity timeout, so every chunk the peer sends resets it. readReply() itself has no deadline, no AbortSignal and no cap on the input buffer or on the accumulated reply lines, so a peer that emits 'NNN-' continuation lines forever (or a stream of bytes containing no CRLF at all) keeps the client inside the data handler indefinitely while both buffers grow. Every protocol step awaits readReply() in sequence, so the whole send never settles.

## `ghosted/verify-token-address-rebind-race`

**Verdict:** `needs_validation` — verifyEmail's address-binding check is a read-then-write outside any transaction, so a token can bind verification to an address it was never issued for if the profile email change commits between the read and the write

The trace holds on re-reading the worktree; the effect is real but conditional, and the decisive fact (whether the interleaving is won in practice) is a runtime property no source reading settles. (1) Statement separation: verifyEmail runs four separate autocommit statements - token SELECT (account.ts:268-277), user SELECT (account.ts:280-283), binding check in application code (account.ts:284-290), user UPDATE (account.ts:293-296), token usedAt UPDATE (account.ts:297-300). Nothing wraps them: no db.transaction, no SELECT ... FOR UPDATE, no conditional predicate on the write. The final UPDATE's WHERE is `eq(users.id, row.userId)` (account.ts:296) - the account id alone, no `AND email = row.email`, no `AND emailVerified = false`. (2) Controls that exist and what they do not cover: users.email is UNIQUE (schema.ts:56), which stops a *second* account at the target address but has no bearing on the write; the token's `email` column (schema.ts:266-277, migration 0015) plus the check at account.ts:284 defeats only the sequential attack; createEmailVerification's delete-all-tokens (account.ts:233-235) runs after the profile email UPDATE commits, so a redemption already past its token SELECT (account.ts:268) proceeds; there is no TRIGGER or FUNCTION anywhere in drizzle/; middleware.ts only redirects, sets X-Robots-Tag and Cache-Control:no-store; there is no re-check after the write and no later reconciliation of emailVerified against the token's address. The two UPDATEs are single-statement transactions, so Postgres row locking serialises them last-writer-wins, and because the WHERE has no email predicate a blocked UPDATE still applies after re-evaluating only `id = X` - i.e. the lock helps the attacker rather than neutralising the race. (3) Payoff chain, verified rather than assumed: classify() branches on the committed flag (oauth-accounts.ts:124-135: emailVerified -> attach, else adopt); the attach branch (oauth-accounts.ts:207-214) inserts the identity only - it does not null passwordHash and does not bump sessionEpoch - whereas adopt (oauth-accounts.ts:216-231) nulls passwordHash, sets passwordDroppedAt and bumps sessionEpoch. Credentials sign-in has no verification gate (lib/auth.ts:129-140 compares only the hash), and the attacker's session survives the email change because updateProfile does not bump sessionEpoch. So if the victim later signs in with Google/LinkedIn over the never-registered target address, the attacker retains a working password on the account the victim now uses; nothing notifies the victim (lib/emails.ts exports only sendEmail, used for verification and reset mail). Both halves of that claim are already pinned as intended in the repo - tests/integration/oauth-accounts.test.ts:130 asserts passwordHash survives attach for a genuinely verified account, and SECURITY.md:113 names exactly that outcome as the harm the address binding exists to prevent. Had the flag stayed false, the victim's provider sign-in would have adopted the account and dropped the attacker's password. Without any provider sign-in the attacker ends up holding nothing the victim ever used: the victim registers, gets 409 EMAIL_TAKEN, and the forgot-password reset replaces the password and bumps sessionEpoch (account.ts:146), evicting the attacker. (4) Accelerator and window: the verify-email GET has no limiter at all - route.ts imports nothing from lib/utils/rate-limit and the file is 31 lines - so docs/API.md:185 ('rate limited per IP') overstates the route. But the accelerator does not widen a single window; it multiplies parallel attempts, and real parallelism is capped by DB_POOL_MAX (default 10 per process, db/client.ts:32). The window itself is the gap between the token's user SELECT (account.ts:280-283) and the user UPDATE (account.ts:293-296) - one database round trip plus any Node event-loop delay - during which the profile UPDATE must commit. A repeat attempt costs a mail round trip, because after a failed attempt the account sits at the target address and a fresh token for the attacker's own address must be mailed and read. So the window is real, narrow, and load-sensitive; it is not made wide by flooding, and the flood is not the bottleneck. (5) Verdict and ceiling: needs_validation. The trace survives adversarial re-reading, no framework, config, database or documentation control neutralises it, and the intent is unambiguous (SECURITY.md:108-115, schema.ts:266-276, account.ts:240-243, tests/integration/account.test.ts:517-522), so this is not a documented trade-off and no trade-off ceiling applies. The honest ceiling is set by three preconditions: the target address must have no account at the moment of the PATCH (unique constraint schema.ts:56 plus the 409 in updateProfile, account.ts:47-58) - so this is a pre-registration squat on an address nobody has claimed, never a takeover of a live account; the interleaving must be won against the deployed Postgres and whatever pooler sits in front of it; and the victim must later sign in with a provider rather than register with a password or reset. What the attacker gains is durable, silent password access to an account the victim believes is theirs - a genuine boundary crossing, but conditional on all three, and revocable by the victim's own reset at any point. What settles it is a live measurement of the win rate, which this pass cannot run.

**Claimed root cause.** verifyEmail reads the account's current email (lib/services/account.ts:280-283) and compares it to the address the token was issued for (lib/services/account.ts:284), but the write that follows updates users by id alone (lib/services/account.ts:295-296). An email change that commits between those two statements leaves the binding check satisfied on a stale read while the write lands on the new address, so the account ends up verified at an address the token was never issued for - the exact state the `email` column was added to prevent.

**Evidence**

- `lib/services/account.ts:296` — The decisive line: the only predicate on the final UPDATE is `eq(users.id, row.userId)`. A conditional form (`and(eq(users.id, ...), eq(users.email, row.email))`) would have closed it with no other change.

- `lib/services/account.ts:262` — The docstring claims the safe direction ('Failing closed is the safe direction'), which is the intent; the implementation enforces it with an application-level check rather than with the write, and the intent is not what runs.
- `lib/services/account.ts:62` — updateProfile sets emailVerified=false and emailVerifiedAt=null in the same UPDATE that moves the address, so the race's later write is provably an override of a deliberate reset rather than an omission.
- `lib/db/schema.ts:56` — users.email is unique. This bounds the attack to addresses with no account (the 409 at account.ts:47-58 fires otherwise) and is the main reason the finding is a pre-registration squat, not a takeover of a live account.
- `lib/db/schema.ts:273` — The column docstring states the binding is 'Compared at redemption', which is true but silent about atomicity - the control as documented is a comparison, and a comparison is exactly what a race defeats.
- `SECURITY.md:108` — 'Verification tokens are bound to the address they were issued for' is presented as the control that closed the squatter-to-attach path. The sequential path is closed; the racy one is not. Nothing in the file accepts the residual race.
- `docs/reviews/security-audit-2026-10-14.md:193` — The earlier audit records this bug's sequential form as 'confirmed / Fixed' by migration 0015 plus the compare. The fix is real; the atomicity gap is what the fix left behind.
- `SECURITY.md:99` — 'One write contract, whichever door the data comes through' records the project's own precedent of moving a check inside the transaction that writes to close a check-then-act race (also docs/CHANGELOG.md:165). The same remedy is missing here, so no implicit trade-off can be read into it.
- `tests/integration/account.test.ts:517` — The test pins the sequential order only (direct db.update of the address at :530-533, then redemption). Its comment at :518-522 states the exact payoff, which means the consequence is understood and intended to be prevented - the gap is coverage, not intent.
- `tests/integration/oauth-accounts.test.ts:130` — Pins that attach leaves passwordHash non-null for a genuinely verified account, and :191 pins verified->attach. So the downstream consequence of forcing the flag is intended behaviour applied to a forged precondition.
- `lib/utils/api.ts:95` — requireSessionForWrite does not consult emailVerified - it refuses only unauthenticated callers and mustChangePassword accounts, plus a 300/hour per-account write budget. It neither prevents nor meaningfully slows a race attempt.
- `lib/db/client.ts:32` — DB_POOL_MAX defaults to 10, capping the attacker's real concurrency per app process - the reason the unthrottled GET multiplies attempts rather than widening the window.
- `docs/API.md:185` — Documents 'rate limited per IP' for GET /auth/verify-email; the route implements none. The accelerator is real (the documentation is wrong about it), but it is a rate-limiting gap, not the mechanism.
- `lib/auth.ts:129` — Credentials sign-in selects the user by email and compares the password hash only - no emailVerified gate. After the race, the attacker's password still signs in at the address the victim believes is theirs.
- `lib/auth.ts:188` — The provider gate refuses only an explicit `email_verified === false`. A Google-verified victim therefore proceeds to the attach branch, which is where the attacker's retained password becomes durable.

**Blockers**

- No execution in this pass: whether the interleaving is actually won against the deployed Postgres cannot be measured from source, and the brief provides no sandbox (and no isolated scratch database I am willing to create tables in). The mechanism is certain from the SQL; the win rate is not.
- The deployment's connection shape in front of Postgres is unknown: a transaction-mode pooler (pgbouncer) or a single pooled connection per process changes how the two UPDATEs interleave and how much real parallelism an attacker gets. DB_POOL_MAX defaults to 10 per app process, which caps the flood.
- Whether the target address is unregistered at the moment of the attempt is a live-world fact, as is whether the victim's first interaction with the instance is a Google/LinkedIn sign-in rather than a password registration. Both preconditions decide whether the forged flag converts into durable access.
- The per-process rate-limit counters (lib/utils/rate-limit.ts) are in-memory, so the hosted replica count multiplies both the write budget and the reachable concurrency - unknown from the repository.

**Validation plan (local).** Against a local Postgres with the app running: create an unverified account at attacker@local.test, redeem nothing, then fire the profile PATCH (email -> victim@local.test) and a burst of concurrent GET /api/auth/verify-email?token=<the attacker's own token> from the same client, tuning the offset between the two. Afterwards read users.email and users.emailVerified directly - a win is email=victim@local.test with emailVerified=true. Repeat N times to estimate the win rate, and vary the offset and burst size to find the boundary. Then, with the win in hand, run resolveOAuthUser for a Google profile with email=victim@local.test and assert the outcome is attach, that passwordHash is still non-null and that a credentials sign-in with the attacker's password still succeeds.

## Correction, third pass (2026-10-14)

Two statements in this file's records lean on a premise the third pass refuted by
measurement in Chrome 154: that a same-site sibling subdomain carries the session
cookie because `SameSite=Lax` permits it. `@auth/core` 0.41.3 sets
`authjs.session-cookie`(-token) with **no `Domain` attribute** and the app sets no
`cookies` override, so the cookie is **host-only** and never reaches a sibling
subdomain — with a control cookie carrying `Domain=` arriving on the same hop,
proving the hop was same-site and that `Lax`, not scoping, is not the reason.

Consequence for this pass's own conclusions: the same-site-sibling-subdomain
foothold cannot attach the session cookie, so the CSRF residual rated LOW
(`ghosted/csrf-missing-on-write-routes` and the residual of
`ghosted/login-csrf-custom-login-route`) requires **XSS on the app's own origin**,
or a deployment that deliberately sets a domain-scoped cookie, rather than merely a
sibling host. The rejected verdicts themselves are unchanged; only the reachability
sentence is narrower. The matching code comment lives at
`app/api/auth/account/route.ts:27`.
