# 1. Verdict

Not yet safe to run unattended for strangers, though far better than the typical solo-dev self-host branch — the prior review round visibly fixed real things. The single most serious problem left is that `app/robots.ts` and `app/sitemap.ts` rely on `export const dynamic = "force-dynamic"` to stay per-request, but nothing in CI actually builds the production image and curls `/robots.txt` to prove it — the exact regression class (build-time baking shipping hosted defaults into a self-hosted container) that an earlier round already found once. The STARTTLS handshake and the full Docker/compose boot sequence are both explicitly unverified by the authors themselves. Everything that touches cross-account data (import, deletion guard, session seam) looks carefully scoped. Ship it only after the three items in §5.

# 2. Findings

1. **STARTTLS success path is still unverified end-to-end, and the socket-close target is ambiguous under failure.** `sendSmtpMessage` upgrades to TLS, builds a new `SmtpSession` around `upgraded`, sets `active = upgraded`, and the `finally` block does `active.end()` — this looks fixed from the earlier review's "closes the wrong socket" finding, but the test suite's own comment admits: `"Only the pre-handshake half is testable here... What this pins is the decision and the write... plus a clean failure when the upgrade cannot happen."` No test exercises a successful STARTTLS→EHLO→AUTH→DATA round trip. This is the path most real providers (port 587) use.
   Evidence: `lib/email/smtp.ts:293-300` (`active = upgraded; ... return await authenticateAndSend(secureSession, ...)`), `tests/unit/smtp.test.ts` ("asks for STARTTLS" test only reaches the handshake failure)
   Severity: major
   Effort: M

2. **`robots.ts` / `sitemap.ts` correctness depends entirely on `dynamic = "force-dynamic"` being honored, and this is asserted only by an e2e test against the dev server, not against a built image.** The changelog itself records that this exact bug (robots.txt baked at build time, serving hosted defaults into a self-hosted container) was found and fixed once already in this same branch's history (`f8b6b66`). The current fix is a one-line export with no test that builds `next build` and inspects the static vs. dynamic route table for these two specific routes. A regression here silently un-noindexes someone's job hunt.
   Evidence: `app/robots.ts:17` (`export const dynamic = "force-dynamic";`), `docs/reviews/code-review-selfhost-2026-09-30.md:33-37` (prior finding #2)
   Severity: major
   Effort: S (add a build-output assertion, e.g. grep the `next build` route table for `ƒ /robots.txt`)

3. **The owner bootstrap password is logged in full to stdout with no redaction, and retention is documented but not enforced.** `ensure-owner.mjs` prints `password: ${password}` whenever no `GHOSTED_USER_PASSWORD` is supplied. The doc comment says "printed once... never stored in plain text" but any log driver (journald, `json-file`, a shipped-off aggregator) retains it indefinitely. This is accepted as a documented risk, but a solo operator following the three-command quickstart is unlikely to read the troubleshooting section before their first login.
   Evidence: `scripts/ensure-owner.mjs:92-96` (`log(\`Created the owner account ${name} <${email}> — password: ${password}\n...\`)`)
   Severity: minor (documented, with a real mitigating idempotency guarantee)
   Effort: M (force password change on first login — already tracked as deferred)

4. **Import's per-application milestone insert loop runs inside one open transaction for up to 5,000 applications.** Even though it's now one `insert(...).values([...])` per application (batched across milestones, fixed from the prior round's per-row issue), it is still up to 5,000 sequential awaited round trips holding open one transaction. On a modest self-hosted Postgres this can hold row/table locks for an extended period; the cap is generous enough (5MB / 5,000 apps) that a legitimate large export could matter.
   Evidence: `lib/services/import.ts:150-193` (the `for (const app of file.applications)` loop, each iteration doing an `await tx.insert(applications)...` plus a conditional `await tx.insert(milestones)...`)
   Severity: minor
   Effort: M

5. **The deletion guard reads `ALLOW_REGISTRATION` directly from `process.env` rather than through any shared parser inside the route, duplicating the "unreadable flag → treat as closed" logic locally.** This is a correct, carefully-reasoned fail-safe (comment explains it well), but it means there are now three independent readers of boolean deployment flags (`lib/config/flags.ts`, `lib/config/flag-parse.ts`/middleware, and this route's local try/catch around `readBooleanFlag`). A future change to the "safe direction" policy has to be remembered in three places.
   Evidence: `app/api/auth/account/route.ts:28-35` (`let registrationOpen = true; try { registrationOpen = readBooleanFlag(...) } catch { registrationOpen = false; }`)
   Severity: nit
   Effort: S

6. **Health endpoint's config check calls `readConfig()`, which re-validates the entire deployment including email transport — a transient Resend outage or key rotation would flip `/api/health` to 503 even though the database and the app are both fine.** The route correctly logs details server-side only, which is good, but conflating "deployment config is internally consistent" with "service is up" means an orchestrator configured to restart on failed healthchecks could cycle a perfectly running container because of an unrelated email misconfiguration.
   Evidence: `app/api/health/route.ts:27-34` (`readConfig()` called inside the health check, independent of the database check)
   Severity: minor
   Effort: S

7. **`Shot` component's `<picture>` lazy-loading contract is enforced only by one Playwright assertion on the default (light) color scheme; the dark-mode payload path (which is `display:none` via CSS, not conditionally rendered) is never measured.** If a future change adds `priority`/`eager` to any dark variant, or CSS specificity changes so `hidden dark:block` no longer actually hides the element from layout, the regression would only show on a dark-mode visit, which the suite does not drive.
   Evidence: `tests/e2e/seo.spec.ts` (`page.on("response")` test only runs under default light colour scheme), `components/LandingMock.tsx` (`className={cn("w-full", theme === "dark" ? "hidden dark:block" : "block dark:hidden")}`)
   Severity: nit
   Effort: S

# 3. Stability under deployment

**Boot sequence.** `scripts/migrate-on-start.mjs` takes an advisory lock, runs migrations, then calls `ensureOwnerAccount`, then releases the lock — correct ordering for a single container, and the lock plus `ON CONFLICT (email) DO NOTHING` plus `RETURNING` makes concurrent-boot races against the owner row safe even if two replicas start together (the `INSERT...ON CONFLICT...RETURNING` pattern is exactly right here, better than the earlier SELECT-then-INSERT this review history says was fixed). What's *not* covered: if migrations fail partway (a bad migration file, a lock timeout under genuinely concurrent multi-replica boot), the container exits per the docs, but there is no test exercising a failed-migration boot path, and the advisory lock is taken on the migration client but the app's own pooled connection (`db` in `lib/db/client.ts`) is separate — a request arriving in the gap between container "started" and "migrations finished" would hit whatever Next.js serves before `migrate-on-start.mjs` completes, which depends entirely on the container's start command ordering (not shown in this diff, only referenced in `docker-compose.yml`'s healthcheck `start_period: 90s`). That 90-second grace period is a reasonable mitigation but not a guarantee on a slow disk.

**DB down / slow.** `/api/health` correctly surfaces this as 503 with the database check separated from a pure "is the process alive" check — good. But ordinary page requests (dashboard, settings) have no equivalent: a dashboard load during a database outage will throw inside a server component and surface as Next's generic error boundary / 500, which is acceptable but not graceful. No evidence of a global timeout or circuit breaker on `db.execute` elsewhere; this review can't confirm whether a slow (not down) database produces a hung request, since no query timeout configuration appears in the diff.

**Prerendering vs. runtime decisions — the exact thing you asked about.** The architecture is sound in principle: `middleware.ts` reads `SHOW_LANDING` and `SITE_INDEXABLE` live per request via the dependency-free `flag-parse.ts`, and `/api/config/analytics` reads `siteIdentity()` live. The root layout and `/` are genuinely static (verified per your claims). The residual risk is exactly finding #2: `robots.ts` and `sitemap.ts` are *not* middleware, they're metadata routes that Next treats specially, and their dynamism depends on a single export per file rather than the shared middleware mechanism. If either loses its `force-dynamic` export in a refactor, the self-hosted instance would serve the **build environment's** robots.txt/sitemap — which, per the Dockerfile's documented build process (no runtime env at build time), would default to the hosted shape's `indexable: true`. That is precisely "a self-hosted instance ends up serving the hosted instance's... indexability." The canonical URL and tracker cannot leak this way: canonical/`og:url` are explicitly build-time by design and documented as such (`siteOrigin()` baked at build, requiring a rebuild to change — intentional and documented, not a bug), and the tracker is proven absent from static HTML by the Analytics-after-hydration design plus the e2e test.

**Upgrade behaviour.** All new flags default to the pre-existing hosted shape (`SHOW_LANDING=true`, `ALLOW_REGISTRATION=true`, email falls back to Resend-or-log exactly as before), and `readSiteIdentity` keeps the hosted Umami tracker with zero new configuration — this is explicitly tested (`site-identity.test.ts`: "keeps the hosted instance's own tracker with no new configuration"). This is a genuinely well-executed no-op upgrade path for the hosted instance. For a self-hosted upgrade, migrations run automatically on every container start, with no rollback mechanism documented beyond "take a pg_dump first" — acceptable for a documented solo tool, not acceptable for anything with an SLA.

**Unbounded surfaces.** Import is well-bounded: streamed body capped at 5MB enforced on the stream itself (not the `Content-Length` header, which is correctly treated as untrustworthy), Zod schema caps array sizes and string lengths. SMTP has a 20-second reply timeout per operation. The health/robots/sitemap routes have no size concerns. The one soft spot is the import transaction's wall-clock duration under the 5,000-application ceiling (finding #4) — bounded in *size* but not in *lock duration*.

# 4. Security boundaries

**Session seam.** `lib/auth/current-user.ts` is a clean single point (`getCurrentUser`/`requireUser`), and the diff shows every prior direct `auth()` call site (dashboard layout, dashboard page, settings page, both image proxy routes, the API guard) migrated through it. `requireUser()` redirects to `/login` for pages; `getCurrentUser()` returns null for API routes to decide themselves, and `lib/utils/api.ts`'s `requireSession()` throws a proper 401 `ApiError`. This is enforced consistently; I did not find a route that skipped it.

**`/api/config/analytics`.** Correctly unauthenticated and correctly so — the response is two public strings (a script URL and a website id), explicitly reasoned in the comment as "nothing here is a secret." `Cache-Control: no-store` is set so flag changes take effect without a cache TTL gap. `Analytics.tsx` injects the returned `src` as a `<script>` tag's `src` attribute, not as `innerHTML` or an eval — this is not an XSS vector unless an attacker controls `UMAMI_SRC`/`UMAMI_WEBSITE_ID`, which are operator-controlled env vars, not user input. Fine.

**Import path.** Authenticated first (`requireSessionForWrite` before the body is even read — correct ordering). Body-size enforcement is on the stream, not the header, closing the TOCTOU gap a header-only check would leave (and there's a dedicated test for the no-Content-Length case). Zod schema bounds everything meaningfully (string lengths, array counts, enums). Transaction boundary is correct: `replace` mode's delete-then-insert happens inside one `db.transaction`, so a mid-import failure leaves the account exactly as it was. Cross-account leakage: row ids from the uploaded file are validated by the schema but *never used* for inserts — fresh UUIDs are always generated, and every delete/select is scoped by `eq(applications.userId, userId)` from the session, not from the file. I checked this specifically and found no path where a crafted file's content can address another user's rows. Idempotency: timestamp-based identity keys handle the common (real export) case correctly; the timestamp-less fallback correctly degrades to company+role matching, with the tradeoff openly documented and tested (two genuinely-distinct no-timestamp applications to the same company/role collapse — acceptable, documented, tested).

**SMTP client.** TLS: implicit TLS (`smtps://`) uses Node's default certificate verification, no `rejectUnauthorized: false` anywhere — good. STARTTLS is now mandatory when `smtp://` is used and the server doesn't advertise it (fixed from the prior round's cleartext-credential finding) — refusal path is tested, success path is not (finding #1). Credentials: parsed via `decodeURIComponent` from the URL, never logged, and the parse-failure error message was fixed to not echo the raw URL (`"SMTP_URL is not a URL"` with an explicit comment about not leaking the password) — this closes a real finding from the prior round. Header injection: `From`/`To` are explicitly guarded with `assertSingleLine`, and `Subject` now gets the same guard (`assertSingleLine(subject, "subject")` in `buildMessage`) — this closes another prior-round finding. Dot-stuffing and CRLF normalization are implemented and have a dedicated regression test that caught a real LF-normalization bug per the changelog.

**Container.** `.dockerignore` excludes `.env`, `.git`, `node_modules`, `.next` — closes the "shipped secrets in image layers" class of problem. Postgres is bound to `127.0.0.1:5432` under the `dev` profile only and not published at all under `selfhost` — this is a real fix over the "exposed Postgres with a public password" finding both other reviewers raised previously; I verified this in the diff (`docker-compose.yml`: `profiles: ["dev", "selfhost"]` for `db`, loopback-only port under the shared service, with `selfhost`'s `app` service reaching it over the compose network, no published port for the app-only case beyond `8080:8080` which is the intended ingress). `AUTH_SECRET` is required via Compose's `${AUTH_SECRET:?...}` syntax, failing the whole `up` command rather than starting with a placeholder — good. No `USER` directive is visible in this diff (the `Dockerfile` itself isn't shown in full in the diff, only referenced), so whether the container runs as root cannot be confirmed from this diff alone — flag as unverified rather than a finding.

**Deletion guard.** Server-enforced (not just a hidden button), reads one flag freshly rather than cached config, and treats an unreadable flag as "closed" — the conservative, safe-by-default direction for a destructive endpoint. The one caveat: it guards on "registration is closed," not "there is exactly one user," so an instance that closed registration after creating three accounts blocks deletion for all three, which is overly conservative but not a security hole.

# 5. What I would not ship without changing

- **Prove the STARTTLS success path against a real or realistic test TLS cert** — right now only the refusal-to-degrade path is tested; the actual encrypted send is not.
- **Add a CI step that runs `next build` with no runtime env and asserts `/robots.txt` and `/sitemap.xml` are dynamic (`ƒ`) in the route table** — this exact class of bug has already bitten this branch once.
- **Force a password change on first login for the bootstrapped owner account**, or at minimum shorten the exposure window (e.g. expire the generated password after first successful auth) rather than relying on an operator reading the troubleshooting doc.

# 6. False alarms

- **"The compose file still exposes Postgres"** — looks alarming at a glance (port 5432 is in the file), but on closer read the `db` service's port binding is loopback-only and shared with the `dev` profile only for the host's own dev server; the `selfhost` profile's `app` service reaches `db` over the compose-internal network and the port is not published under that profile's actual deployment path. This was a real finding in the prior round and is now fixed.
- **"Import has no rate limiting"** — not true; `requireSessionForWrite("import")` applies the same per-user write throttle used elsewhere (documented as rejected by the merged review already, and consistent with this diff).
- **"`og:url`/canonical being baked at build time is a self-host bug"** — this is intentional and documented (`siteOrigin()` is explicitly described as build-time, requiring a rebuild for a custom domain), unlike the robots.txt/sitemap case which is supposed to be runtime. Different contract, correctly implemented for its own purpose.
- **"The owner password reaches `docker inspect`"** — only true for the explicit `GHOSTED_USER_PASSWORD` override path, which is documented as being for scripted setups where the operator already controls that secret; the default (random, printed once) path never puts the password in the environment at all.
