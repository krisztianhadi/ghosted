# Ghosted 1.0.0

**A job-application tracker you can run yourself.** Every application, every
interview step, and a signal when one goes quiet — on your own database, under
your own domain, with an export you own.

This is the first release, and it is deliberately the point where four things are
true at once: the app works, it can be self-hosted by a stranger, it can be found
by a search engine, and the machinery that keeps it that way runs without a human
remembering to.

## Run it

```bash
git clone https://github.com/krisztianhadi/ghosted && cd ghosted
cp .env.example .env      # set AUTH_SECRET: openssl rand -base64 32
docker compose --profile selfhost up -d --build
```

Then open `http://localhost:8080`. The instance creates its owner account from
`GHOSTED_USER_EMAIL` on first boot and prints a one-time password to the log —
which you must replace at first sign-in before the account can write anything.
The full walkthrough, including TLS, email and backups, is
[docs/SELFHOST.md](../SELFHOST.md).

Hosting it yourself is a supported shape, not a degraded one: the same image
serves the marketing landing or goes straight to the sign-in screen, allows or
refuses registrations, indexes itself or refuses crawlers, and wears your name in
the footer and imprint instead of the maintainer's — all from environment
variables, decided per request rather than baked at build time.

## What is in it

- **The board.** Applications as cards grouped by stage, with the quiet ones
  called out, plus a list view.
- **Milestones per application.** The interview trail, with dates and comments.
- **Your data, in and out.** A versioned JSON export, and an import that merges
  into an existing account — the reason it exists is that a tracker you cannot
  leave is not a tracker you can trust.
- **Email that is provider-neutral.** Resend, any SMTP server, or a log stub for
  a solo instance that does not want to send at all.
- **Self-hosting that behaves.** Two flags (`SHOW_LANDING`, `ALLOW_REGISTRATION`),
  a boot-seeded owner, migrations that run once under an advisory lock, a health
  probe that checks the database *and* the deployment configuration, and a
  container that runs as `node` with no `.env` inside it.
- **Search-engine hygiene.** A real title, canonical URLs, a sitemap, structured
  data, and a landing that ships 79 KB of screenshots instead of 903 KB because
  the variants it is not showing are never fetched.

## What is verified, and how

- `pnpm lint`, `pnpm typecheck`, **351** unit and integration tests, **47**
  end-to-end tests in a real browser (including axe accessibility checks).
- CI builds the container, boots the documented compose stack, and asserts the
  instance's behaviour: healthy with a coherent config, `/` redirected when the
  landing is off, crawlers refused, registration closed to strangers, and the
  image optimizer refusing URLs it does not own.
- The build asserts its own shape — that the landing stayed prerendered and that
  the pages which read the environment did not get baked into the image.
- The dependency audit is clean and blocking in CI: the one remaining advisory is
  listed in [SECURITY.md](../../SECURITY.md) with the reason it is accepted.
- **The staging environment was verified end to end** before `main` was touched:
  `/api/health` answering `{"ok":true,"database":"up","config":"ok"}`, the
  landing served with a canonical URL of its own, `noindex` plus a disallowing
  `robots.txt` and an empty sitemap, registration answering `403`, the image
  optimizer refusing remote URLs, and a real sign-in as the boot-seeded owner
  landing on the forced password change — with writes refused
  (`403 PASSWORD_CHANGE_REQUIRED`) until it is replaced.

## Known limitations

- **`next lint` is deprecated** and will be removed in Next.js 16; the migration
  to the ESLint CLI is scheduled, not done.
- **A prebuilt image bakes `NEXT_PUBLIC_APP_URL`** into the canonical URL, the
  `og:url` and the JSON-LD `url`. Building your own image — which the command
  above does — is unaffected.
- **The STARTTLS handshake has not been run against a real provider's
  certificate.** The refusal path, the deadline and the success path against a
  self-signed certificate are covered by tests; a live SMTP account is not.
- No metrics endpoint, no multi-user administration, no i18n. None of those are
  promised.
